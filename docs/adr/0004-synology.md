# ADR 0004. Публикация на Synology: HTTPS в Caddy, готовые сборки, установка задачей DSM

Дата: 2026-10-14, пересмотрено 2026-10-15. Состояние: принято.

## Контекст

Человек публикует DocFlow на своём Synology в офисе: сайт открывают из
интернета по имени `*.synology.me`, данные переносятся из базы
разработки, ставить хочет «как своего бота» – мышкой, без SSH.

С ADR 0002 изменилось главное: вход, учётные записи, компании и персонал –
на сервере на Go с PostgreSQL. Публикации одного сайта (`deploy/`) мало:
без сервера API вход не работает.

Что выяснилось по ходу (14–15.10):

- **DSM 6.2 и пакет Docker**, а не DSM 7.2 с Container Manager. Обновлять
  DSM человек не будет.
- **DSM 6.2 без исправлений безопасности с 01.10.2024** – в том числе её
  веб-сервер nginx, который в DSM 7 служил бы обратным прокси.
- В пакете Docker для DSM 6.2 нет «Проектов» (docker-compose из
  интерфейса), а `docker-compose` – первой версии (1.28.x): нет top-level
  `name`, нет условия `service_completed_successfully`.
- Порты 80 и 443 на NAS занимает nginx DSM.
- Процессор NAS слабый, бывает x86_64 и aarch64.
- Docker на машине разработчика не работает (нет WSL) – образы здесь не
  собрать и не запустить.

## Решение

1. **HTTPS держит Caddy в контейнере**, а не DSM. Сертификат Let's
   Encrypt на имя synology.me Caddy получает и продлевает сам: проверка
   TLS-ALPN на 443, HTTP-проверка выключена (порт 80 наружу не открыт).
   Роутер: внешний TCP 443 → NAS 8443 → 443 контейнера. DSM 6.2 из
   интернета не видна вовсе. HTTP/3 выключен (UDP не пробрасывается).
2. **Адрес клиента – само соединение.** Прокси между интернетом и Caddy
   нет; `X-Real-IP` и `X-Forwarded-For` от клиента не принимаются. Серверу
   API Caddy передаёт адрес одним значением `X-Forwarded-For`.
3. **Сборка – на компьютере разработчика** (`scripts/deploy/pack-synology.ps1`):
   из последнего коммита, после тестов сайта и сервера; сервер – для
   `amd64` и `arm64`. Образы на NAS только копируют готовые файлы
   (`caddy:2.11-alpine`, `gcr.io/distroless/static-debian12:nonroot`);
   архитектуру NAS и признак «исполняемый» задаёт сборка образа
   (промежуточный `busybox`, `uname -m`). Все образы – alpine или
   статические: со старым Docker на DSM 6.2 у образов на новом glibc
   бывают сбои.
4. **База – `postgres:18-alpine`** в томе Docker, наружу не публикуется.
   18 – как в разработке: копия из 18-й в 16-ю не ложится (`CLAUDE.md`
   требует 16+). Миграции – отдельный контейнер владельцем базы;
   приложение – ролью `docflow_app` без `BYPASSRLS`.
5. **Установка и обновление – `deploy/synology/install.sh` разовой задачей
   Task Scheduler DSM от root (задача DocFlow install).** Проверяет Docker 20.10+, docker-compose
   1.28+ и `.env`, затем по порядку: сборка, база, `docflow-init`
   (`db.sh init`: пароль `docflow_app` по `.env`; перенос копии из
   `docflow/import` только в пустую базу одной транзакцией; копия базы
   перед миграциями), `migrate`, сервер и сайт, проверка HTTPS. Журнал –
   `docker/docflow-install.log`, виден в File Station. Порядок задаёт
   скрипт, а не `depends_on`: docker-compose 1.28 не умеет ждать
   завершения контейнера. `init` и `migrate` – в профиле `setup`, чтобы
   простой `up` их не запускал.
6. **`.env` готовит `scripts/deploy/make-env.ps1`** на компьютере
   разработчика – в `%LOCALAPPDATA%`, не в OneDrive. Пароль на сайт в нём
   открытым: хеш считает `web-start.sh` при запуске Caddy.
7. **Пароль на сайт** остаётся, кроме `/api/*`. После верного пароля –
   пропуск: cookie `docflow_gate` (HttpOnly, Secure, 30 дней) со случайным
   ключом из `.env`. Без него сайт не работал бы: браузер подставляет
   запомненный пароль сайта и в `fetch` к `/api`, а на ответ 401 от API
   («нужно войти», «неверный логин или пароль») забывает его и спрашивает
   снова на следующем файле сайта. Найдено сценарием в Chrome 14.10.
8. **Копии базы** – ночью задачей DocFlow backup в Task Scheduler
   (`docker exec docflow-db bash /docflow/db.sh backup`) и при каждой
   установке до миграций; 14 последних; дальше – Hyper Backup.
9. **Имена контейнеров и сети постоянные** (`docflow-db`, `docflow-api`,
   `docflow-web`, сеть `docflow`): команды инструкции не зависят от имени
   проекта.

## Альтернативы

- **Обратный прокси DSM с её сертификатом** (первая версия, 14.10). Хорош
  на DSM 7.2; на DSM 6.2 открыл бы интернету веб-сервер системы без
  исправлений безопасности. Отклонено.
- **Проект Container Manager** (вторая версия, 14.10). В пакете Docker для
  DSM 6.2 его нет. Возвращается, если NAS переведут на DSM 7.2: тот же
  `docker-compose.yml` для него годится, порядок тогда задаёт `install.sh`
  так же.
- **Скрипт установки по SSH** (первая версия). Работал, но человек хочет
  без SSH; та же работа – задачей Task Scheduler.
- **Сборка из исходников на NAS** (как в `deploy/` для VPS). Нужны образы
  Node и Go (~1,5 ГБ) и 2+ ГБ памяти на сборку; на NAS уходит не то, что
  прошло тесты. Отклонено.
- **PgBouncer, Redis, MinIO** (стек в `CLAUDE.md`). Сейчас один процесс API
  с пулом 10 соединений, очередей и файлов на сервере нет. Отложено до
  этапов, где они нужны. Для PgBouncer понадобится правка `db.Open`:
  `statement_timeout` передаётся параметром подключения, который
  PgBouncer по умолчанию отвергает.
- **Cloudflare Tunnel** без проброса портов. Нужен, если у офиса «серый»
  IP. Описан в инструкции как запасной путь.
- **Хеш пароля на сайт – на компьютере разработчика.** Нужен bcrypt, а
  его нет ни в PowerShell, ни в зависимостях сайта; считать его при
  запуске Caddy проще, а пароль на сайт и так известен всем сотрудникам.

## Последствия

- Обновление – новый пакет, File Station → Extract поверх, задача
  DocFlow install → Run; пароли, данные и сертификат остаются.
- `.env` нельзя пересоздавать после первого запуска: пароль владельца
  база запоминает при создании тома (`make-env.ps1` без `-Force` откажет).
- Из офиса сайт по имени открывается, только если роутер умеет NAT
  loopback; иначе – локальный DNS и порт 8443.
- Если Docker на NAS подменяет адрес посетителя (userland-proxy),
  ограничение частоты входа станет общим на всех – проверяется в разделе 7
  инструкции.
- **Не проверено на этой машине:** сборка образов и запуск на Docker
  20.10 DSM 6.2, ограничения контейнеров на ядре DSM, выпуск сертификата
  Let's Encrypt, команды `docker exec` из инструкции. Проверка – разделы
  6–7 `docs/deploy-synology.md`.
- `deploy/` (VPS) публикует только сайт и устарел, пока не получит сервер
  API и базу так же.
