# Проверка безопасности, 29–30.09.2026

Что проверено, что найдено, что исправлено и что осталось. Задача
человека: «проверь безопасность инструментами, безопасность должна быть на
высшем уровне».

## Коротко

- **Главный риск не закрыт и не закрывается без сервера.** Вход, пароли и
  права сейчас проверяет браузер. В Chrome подтверждено: подменой
  `sessionStorage` можно войти администратором без пароля, а все данные
  лежат в `localStorage` открытым текстом. Это не ошибка, которую можно
  поправить, а свойство нынешней архитектуры. Закрывает её серверный этап
  (`docs/plans/phase-01-server.md`). До него сайт защищён паролем на весь
  сайт: без него чужой не получит даже код.
- **Репозиторий на GitHub публичный**, в нём реальные реквизиты компаний
  (БИН, счета). Сделать приватным может только владелец.
- Всё остальное, что нашлось, исправлено и проверено (таблица ниже).

## Что проверено и в порядке

- Без пароля сайта – 401 на всё: страницы, файлы сборки, обход путей
  (`..%2f`), `HEAD`, `OPTIONS`, `POST`. Нет листинга каталогов, карт
  исходников, `.git`, `.env`. `PUT`/`DELETE`/`TRACE` – 405.
- XSS: нагрузки в названии компании, ФИО, полях документа, описании –
  ни одна не выполнилась ни на одном экране, видна как текст.
- CSP: внедрённый встроенный скрипт и скрипт с чужого адреса не
  выполняются, `fetch` наружу заблокирован, в чужую страницу сайт не
  встраивается (`frame-ancestors 'none'`).
- Все экраны, сохранение документа, PDF, архив (загрузка и «Открыть» в
  новой вкладке) – без единой ошибки или предупреждения в консоли при
  строгой CSP, COOP/CORP и новом `Permissions-Policy`.
- Шрифты: грузятся со своего адреса, казахские буквы на месте, ни одного
  запроса к чужим адресам.
- Журнал запросов: пароль сайта в него не попадает (`REDACTED`); подделать
  строку «неверный пароль» с чужим адресом через адрес страницы или
  заголовки нельзя – проверено `fail2ban-regex`.

## Что не проверено

- **Сборка образа и запуск контейнера с ограничениями** и **блокировка
  fail2ban в цепочке `DOCKER-USER`** – на машине разработчика нет Docker.
  `setup-server.sh` прогнан на заглушках (обе ветки: fail2ban встал / не
  встал), `docker compose config` – без ошибок. Проверять на сервере –
  раздел ниже.
- Настоящий сервер: TLS-настройки (у Caddy по умолчанию TLS 1.2+ и
  современные шифры), выпуск сертификата, IPv6.
- Автоматический пентест (Strix) – см. выше.
- Нагрузка и отказ в обслуживании – не проверялись.
- Сам сервер (SSH, обновления ОС) – только рекомендации в
  `docs/deploy.md`, скрипт их не меняет.

## Проверить на сервере после первого запуска

```bash
cd /opt/docflow/deploy
docker compose ps                                   # web – running
docker compose logs --tail 30 web                   # нет ошибок прав доступа
curl -sI https://ДОМЕН/ | grep -iE 'HTTP|server|content-security'
                                                    # 401, CSP есть, Server нет
fail2ban-client status docflow-caddy                # защита включена
```

Затем с телефона через мобильный интернет (другой адрес) 10–11 раз ввести
неверный пароль сайта: сайт с телефона должен перестать открываться, в
`fail2ban-client status docflow-caddy` появится адрес, а
`iptables -S DOCKER-USER | grep f2b` покажет правило блокировки. Открыть
адрес: `fail2ban-client set docflow-caddy unbanip АДРЕС`.

Если контейнер не запускается и в журнале `permission denied` или
`read-only file system` – ограничение контейнера оказалось лишним: пришлите
журнал, поправлю (временно можно убрать `read_only: true` из
`deploy/docker-compose.yml`).
