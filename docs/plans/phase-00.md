# План этапа 0 — Каркас

Статус: **черновик, ждёт подтверждения человека.** Код не пишется, пока нет «ок» и ответов на Q1–Q4 из `docs/questions.md`.

Цель этапа (из `docs/roadmap.md`): пустой, но полностью рабочий скелет — все процессы поднимаются и корректно останавливаются, все проверки запускаются одной командой, генерация `.docx` доказана тестом.

В этапе 0 **нет** бизнес-логики: ни компаний, ни пользователей, ни документов. Только каркас и доказательства, что выбранные инструменты делают то, что от них требуется.

## 0. Предусловия (вне кода)

Выполняет человек. Без этого шаги ниже не запускаются.

| Что | Почему |
|---|---|
| WSL2 + Docker Desktop на WSL2-бэкенде | без Docker нет ни `dev`, ни testcontainers |
| Go windows/amd64 (или Go внутри WSL2) | сейчас стоит `windows/386` |
| Перенос проекта из OneDrive в путь без пробелов | OneDrive портит `.git`, пробел ломает часть инструментов |
| Ответы на Q1–Q4 | выбор `task`/`make`, `pnpm`/`npm`, git-remote, шрифты |

### Шаг 0.2. Спайк генерации `.docx` и ADR (делается первым)

Это самый рискованный выбор всего проекта, и он меняет содержимое `docker-compose`, Dockerfile конвертера и контракт `worker → converter`. Поэтому идёт до остального каркаса, а не после.

**Что проверяем — ровно 4 требования из `CLAUDE.md`, на одном тестовом шаблоне:**

1. плейсхолдер, разбитый Word на несколько `run` (`{{emp` + `loyee.name}}`);
2. таблица с повторяющимися строками (спецификация на 3 позиции);
3. картинка (логотип) в колонтитуле;
4. казахские буквы ә ғ қ ң ө ұ ү һ і — сохраняются в `.docx` **и** видны в PDF после конвертации.

**Кандидаты:** чистый Go (`unioffice` — платная лицензия, `go-docx`, `nguyenthenguyen/docx`) против отдельного сервиса рендера в контейнере `converter` (Python `docxtpl` + LibreOffice — этот вариант `CLAUDE.md`, п. 2 прямо разрешает).

Никакой из вариантов заранее не объявляется победителем: побеждает тот, что проходит 4 теста. Тестовый шаблон делается руками в Word и кладётся в репозиторий как эталон.

**Файлы:** `tests/templates/spike/` (шаблон, ожидаемые значения), `docs/adr/0004-docx-rendering.md`.

**Готово когда:** 4 теста зелёные на выбранном варианте, в ADR записано, что именно проверялось и какие варианты отпали и почему. Если ни один не проходит — останавливаемся и выносим на обсуждение, а не подгоняем требования.

### Шаг 0.4. Инфраструктура для разработки

**Файлы:** `infra/docker-compose.yml`, `infra/docker/{backend,converter,web}/Dockerfile`, `infra/postgres/{postgresql.conf,pgbouncer.ini}`, `infra/redis/`, `infra/minio/`, `.env.example`.

**Сервисы:** PostgreSQL 16, PgBouncer (transaction mode), Redis 7, MinIO, ClamAV, converter.

**Важные детали, которые легко пропустить:**

- PgBouncer в transaction mode + `pgx` с подготовленными запросами — заранее решаем конфликт: либо PgBouncer ≥ 1.21 с `max_prepared_statements > 0`, либо `QueryExecModeExec` в pgx. Выбор записывается в ADR-0003 и проверяется тестом, который ходит **через PgBouncer**, а не мимо него.
- ClamAV обновляет базы через интернет — ему сеть нужна. «Без сети» в архитектуре относится только к `converter`, и это значит «нет исходящего интернета», а входящий HTTP от `worker` есть. Формулировку в `docs/architecture.md`, п. 10 поправить.
- В контейнер конвертера кладутся шрифты по ответу на Q4.

**Готово когда:** `task dev` (или `make dev`) поднимает всё с нуля, `task dev` на чистой машине повторяется без ручных действий.

### Шаг 0.5. Миграции и роли базы данных

**Миграции (goose):**

- `0001_extensions.sql` — `pgcrypto`, `citext`; настройки схемы;
- `0002_db_roles.sql` — роль `docflow_app` **без** `BYPASSRLS` (под ней ходит приложение) и роль `docflow_migrate` для DDL. Партиции `audit_log` в будущем создаёт `docflow_migrate` или scheduler под отдельной ролью — у роли приложения прав на DDL нет и не будет.

RLS в этапе 0 не включаем: таблиц компаний ещё нет, это этап 1. Но роли создаём сейчас, потому что от них зависит строка подключения в `docker-compose` и в CI.

**Тесты:** `up → down → up` на чистой базе (testcontainers); проверка, что `docflow_app` не имеет `BYPASSRLS` и не может выполнять DDL.

### Шаг 0.6. Конфигурация, логи, метрики, трассировка

**Файлы:** `internal/config/`, `internal/observability/{metrics,tracing,health}`, `internal/http/middleware/{request_id,logging,recover,timeout}`.

### Шаг 0.8. Процессы и плавная остановка

**Файлы:** `backend/cmd/{api,worker,relay,scheduler,migrate,seed}/main.go`, `internal/app/`, `internal/resilience/shutdown.go`.

На этапе 0 `worker`, `relay`, `scheduler` и `seed` ничего полезного не делают — они поднимаются, подключаются к зависимостям, логируют и корректно завершаются. Это каркас, и так и записано в `PROGRESS.md`; заглушками, выдающими себя за готовое, они не являются.

**Тесты:** на каждый процесс — `SIGTERM` приводит к выходу с кодом 0 за отведённое время, а запрос, начатый до сигнала, успевает завершиться.

### Шаг 0.11. Одна команда для всех проверок

**Файлы:** `Taskfile.yml` (или `Makefile` — по ответу на Q1).

Цели: `dev`, `gen`, `migrate`, `seed`, `test`, `lint`, `check`, `check-catalog`, `load-test`.

`check` = `golangci-lint` + `go vet` + `govulncheck` + `go test -race ./...` + `tsc --noEmit` + линтер и тесты сайта + `check-catalog` + `gen` без diff + миграции `up → down → up`.

`check-catalog` на этапе 0 умеет мало: каталог ещё пуст, проверяются только наличие и схема файлов. Полные правила (профиль, серия, соответствие полей шаблону) появляются на этапе 3. Это записано в «Не сделано» в `PROGRESS.md`, чтобы зелёный `check-catalog` никого не вводил в заблуждение.

**Производительность тестов:** один контейнер PostgreSQL на весь прогон (`TestMain`), схема на пакет. Иначе `go test ./...` поднимет десяток баз и `check` станет невыносимо долгим уже к этапу 2.

## Чего в этапе 0 не будет

Чтобы это не выглядело пропущенным: таблиц компаний, пользователей и документов; RLS (этап 1); наполнения каталога (этапы 3 и 8); загрузки файлов и антивируса в работе (этап 5); очередей с реальными задачами (этап 4); реплики и секционирования (этап 9).

## Риски этапа

| Риск | Чем грозит | Что делаем |
|---|---|---|
| Ни один вариант рендера `.docx` не проходит 4 теста | рушится вся идея шаблонов | шаг 0.2 идёт первым; при провале — останавливаемся и обсуждаем, а не ослабляем требования |
| PgBouncer + подготовленные запросы pgx | падает в проде, а не в тестах | тест ходит через PgBouncer с самого начала |
| Нет WSL2 и Docker | нельзя выполнить ни один критерий приёмки | предусловие, до кода |
| `SET LOCAL` можно забыть | дыра в изоляции компаний на этапе 1 | уже в этапе 0 пул БД прячется внутри `storage/postgres`, наружу торчит только транзакция; репозиторий физически не может получить соединение без транзакции |
| Матрица доступа и рендер всех шаблонов утяжелят `check` до часов | проверки перестанут запускать | решение принимается сейчас: политика доступа проверяется быстрыми unit-тестами, интеграционных — выборка, полный прогон — ночью (этапы 1, 3, 8) |

## Критерии приёмки этапа 0 и чем они закрываются

- [ ] `task dev` поднимает всё с нуля на чистой машине → шаги 0.4, 0.9, ручная проверка на второй машине или после `docker system prune`.
- [ ] `task check` зелёный, CI зелёный → шаги 0.11, 0.12.
- [ ] `/healthz` и `/readyz` отвечают, `readyz` падает при недоступной БД → шаг 0.7, тест останавливает контейнер БД и ожидает `503`.
- [ ] Тест библиотеки docx: разбитый плейсхолдер, повторяющиеся строки таблицы, логотип в колонтитуле, казахские буквы в PDF → шаги 0.2 и 0.9.
