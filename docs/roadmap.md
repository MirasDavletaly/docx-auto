# План работ по этапам

Каждый этап — отдельная ветка и отдельный PR. Следующий этап начинается только когда все критерии предыдущего выполнены и `make check` зелёный. Перед этапом — план в `docs/plans/phase-NN.md`, после — отчёт по формату из `CLAUDE.md` и независимое ревью (см. `docs/prompts.md`).

Все критерии проверяются тестами или командой, а не словами.

---

## Этап 0. Каркас

Цель: пустой, но полностью рабочий скелет, на котором дальше всё строится.

- Структура репозитория из `docs/architecture.md` (раздел «Структура репозитория»).
- `Makefile`: `dev`, `gen`, `migrate`, `seed`, `test`, `lint`, `check`, `check-catalog`, `load-test`.
- `docker-compose.yml`: PostgreSQL, PgBouncer, Redis, MinIO, ClamAV, converter.
- `api/openapi.yaml` с `/healthz`, `/readyz`; генерация Go и TypeScript из него.
- Процессы `api`, `worker`, `relay`, `scheduler`, `migrate`, `seed` запускаются и корректно останавливаются по сигналу.
- Логи (slog, JSON, `request_id`), метрики Prometheus, трассировка.
- Сайт: Vite + React + TS strict, роутинг, пустой layout, клиент API.
- CI: линтеры, тесты, `govulncheck`, проверка `make gen` без diff, сборка сайта.
- ADR: модульный монолит; файлы в S3; мультикомпанийность через `company_id` + RLS; библиотека генерации docx (с тестом всех 4 требований из `CLAUDE.md`).

**Приёмка**
- [ ] `make dev` поднимает всё с нуля на чистой машине.
- [ ] `make check` зелёный, CI зелёный.
- [ ] `/healthz` и `/readyz` отвечают; `readyz` падает, если БД недоступна.
- [ ] Тест библиотеки docx: разбитый плейсхолдер, повторяющиеся строки таблицы, логотип в колонтитуле, казахские буквы в PDF.

## Этап 1. Компании, пользователи, вход, роли, изоляция

- Миграции: `companies` (реквизиты, брендинг), `users`, `roles`, `permissions`, `user_company_roles`, `sessions`, `audit_log`, RLS, роли БД.
- `internal/tenant`: `company_id` из токена в контекст и в `SET LOCAL` каждой транзакции.
- Вход, выбор компании (если ролей несколько), access/refresh, ротация, обнаружение повторного использования, `token_version`, блокировка после 5 попыток, rate limit.
- Права `раздел.профиль.действие`; системные роли из `catalog/roles.yaml` через `seed`; конструктор ролей для админа компании.
- Два уровня админа: платформа и компания. Админ не видит содержимое документов.
- Брендинг: загрузка логотипа, цвета; на сайте тема компании применяется после входа.
- Сайт: вход, выбор компании, layout с логотипом, админка: компании, пользователи, роли.

**Приёмка**
- [ ] Тест: пользователь компании А не видит и не меняет ничего в компании Б — через API и напрямую SQL-запросом под ролью приложения (RLS).
- [ ] Тест: смена ролей или блокировка делает старый токен недействительным сразу.
- [ ] Тест: повторное использование refresh-токена отзывает все сессии.
- [ ] Тест: админ компании не может выдать себе роль и не может управлять другой компанией.
- [ ] Вход под пользователями двух разных компаний показывает два разных логотипа.

## Этап 2. Справочники и календарь

- Отделы (с руководителем), должности, сотрудники с историей изменений по датам, контрагенты (юр. и физ. лица), связь пользователь → сотрудник.
- Шифрование ИИН, окладов, адресов; маскировка; аудит просмотра.
- Проверка ИИН/БИН по контрольной цифре.
- Производственный календарь: праздники и переносы по годам, редактируется админом.
- Краткая карточка сотрудника (для выбора в формах) и полная (для HR и директора).

**Приёмка**
- [ ] Тест: юрист видит краткую карточку сотрудника, но не ИИН и оклад.
- [ ] Тест: в БД ИИН хранится зашифрованным; в логах его нет.
- [ ] Табличные тесты ИИН/БИН (валидные и невалидные).
- [ ] Тест: история сотрудника возвращает правильные данные на любую дату.

## Этап 3. Каталог и шаблоны (пилот на 5 документах)

- Загрузка `catalog/` в БД: разделы, профили, серии, типы документов; `make check-catalog`.
- Шаблоны: общие для всех компаний + переопределение для компании; версии; новая версия не трогает старые документы.
- Сборка формы: авто-поля, поля из справочников, ручные поля; вычисляемые поля (дата окончания отпуска по календарю).
- Рендер черновика в очереди: docx с логотипом и реквизитами компании → PDF с водяным знаком «Черновик».
- «Сумма прописью» ru/kk.
- Сайт: каталог «Создать документ» (только разрешённое), форма из `fields.yaml`, предпросмотр.
- Пилотные документы: приказ о приёме, приказ об ежегодном отпуске, трудовой договор, договор оказания услуг, доверенность.

**Приёмка**
- [ ] Каждый пилотный шаблон × каждая из 4 компаний собирается в тесте; в PDF правильный логотип и реквизиты.
- [ ] `check-catalog` падает, если у документа нет профиля доступа или поле в шаблоне не описано.
- [ ] Каталог показывает пользователю только то, что его роли могут создать (проверено для 3 ролей).
- [ ] Табличные тесты «суммы прописью» на русском и казахском.
- [ ] Дата окончания отпуска учитывает праздники из календаря.

## Этап 4. Документы и согласование

- Создание из шаблона со снимком полей и версией шаблона.
- Статусы: Черновик → На согласовании → Утверждён → Подписан → Архив; Отклонён; Отменён.
- Маршруты из каталога: визы → директор. Участник маршрута получает доступ.
- Нумерация при утверждении; финальный PDF с номером; SHA-256.
- Связи (основание, доп. соглашения), отмена документом, делегирование заместителю.
- `outbox` + `relay`; идемпотентность `POST`; `lock_version`; `FOR UPDATE`.
- Сайт: мои документы, карточка, очередь директора, решение, конфликт `409`.

**Приёмка**
- [ ] Тест: 50 параллельных утверждений одного документа → ровно одно решение.
- [ ] Тест: 100 параллельных утверждений разных документов одной серии → номера подряд, без дыр и дублей.
- [ ] Тест: директор утверждает не текущую версию → `409`.
- [ ] Тест: изменение фамилии сотрудника не меняет уже утверждённый приказ.
- [ ] Тест: работник не видит черновик приказа о себе, но видит утверждённый.
- [ ] Тест: нельзя утвердить документ о самом себе.
- [ ] Тест: событие не теряется при падении процесса между коммитом и отправкой в очередь.

## Этап 5. Файлы и подпись

- Загрузка готовых документов (профиль `external`, положения, устав), входящие с серией Вх.
- Подписанные ссылки, подтверждение с проверкой размера и хеша, проверка типа по содержимому, антивирус, превью, OCR.
- Подпись: бумажная (печать → скан) и ЭЦП через NCALayer с проверкой подписи на сервере.

**Приёмка**
- [ ] Тест: `.exe`, переименованный в `.pdf`, отклоняется.
- [ ] Тест: файл не скачивается до `CLEAN`; заражённый файл уходит в карантин.
- [ ] Тест: подтверждение с неверным размером или хешем отклоняется.
- [ ] Тест: подпись, не соответствующая хешу документа, отклоняется.

## Этап 6. Последствия, ознакомление, реестры

- Эффекты приказов: изменение карточки сотрудника в дату вступления; откат при отмене.
- Ознакомление: в системе или скан листа; кто не ознакомился.
- Реестры и журналы всех разделов: собираются из данных, выгрузка в Excel в очереди.
- Табель: из приказов + ручные правки, закрытие месяца.
- Судебные дела, проекты (карточка + документы).
- Напоминания: доверенности, договоры, испытательный срок, ЕСУТД, документы на согласовании.
- Уведомления: в системе, email, Telegram.

**Приёмка**
- [ ] Тест: приказ о переводе с будущей датой меняет карточку только в эту дату.
- [ ] Тест: отмена приказа откатывает его эффект.
- [ ] Тест: закрытый месяц табеля нельзя изменить без права и записи в аудит.
- [ ] Журнал приказов совпадает с утверждёнными документами (тест на сгенерированных данных).

## Этап 7. Поиск, главные экраны, кэш

- Полнотекстовый поиск PostgreSQL с фильтром доступа в SQL.
- Главный экран для каждой роли; счётчики из кэша.
- Кэш: память процесса (каталог, версии шаблонов), Redis (права, брендинг, счётчики) с инвалидацией через Pub/Sub, ETag/304, настройки React Query.
- Интерфейс журнала аудита.

**Приёмка**
- [ ] Тест: поиск не находит документы чужой компании и чужого раздела.
- [ ] Тест: после смены прав пользователя кэш прав сбрасывается сразу.
- [ ] Повторный запрос каталога возвращает `304`.

## Этап 8. Наполнение каталога

- Все документы из `catalog/source/documents-list.txt`, партиями по разделу (один раздел — один PR).
- Для каждого: запись в каталоге (профиль, серия, маршрут, срок хранения, разделы показа, отметка «влияет на оплату»), `fields.yaml`, шаблон с пометкой `ЧЕРНОВИК ТЕКСТА — ПРОВЕРИТЬ ЮРИСТУ`.
- Документы, которые встречаются в нескольких разделах, — один тип, показ в нескольких разделах.
- Документы профиля `external` не генерируются, только загружаются.

**Приёмка (для каждого раздела)**
- [ ] `check-catalog` зелёный.
- [ ] Каждый шаблон раздела × 4 компании собирается в тесте.
- [ ] Матрица доступа раздела (документ × роль × состояние) сгенерирована и зелёная.
- [ ] Таблица документов раздела с профилями выгружена для проверки руководителю раздела.

## Этап 9. Нагрузка и эксплуатация

- Чтение с реплики, запись в primary; PgBouncer в режиме transaction.
- Секционирование `audit_log`, `outbox`, `notifications`.
- Справедливая очередь и лимиты по компаниям.
- `docker-compose.prod.yml` с несколькими копиями `api`, `worker`, `converter`; nginx-балансировщик; плавная выкатка.
- Мониторинг, алерты, дашборды; бэкапы с восстановлением на любую минуту; еженедельный тест восстановления.
- `docs/runbook.md`, `docs/threat-model.md` (каждая угроза → где закрыта → каким тестом).

**Приёмка**
- [ ] k6: 4 компании одновременно, 500 виртуальных пользователей, 15 минут — p95 API < 300 мс, ошибок < 0,1 %, рендер черновика p95 < 5 с.
- [ ] Остановка одной копии `api` во время нагрузки не даёт ошибок пользователям.
- [ ] Восстановление из бэкапа на отдельном сервере проверено скриптом.
- [ ] Алерты приходят (проверено вручную искусственным сбоем).
