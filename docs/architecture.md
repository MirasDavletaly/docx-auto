# Архитектура DocFlow

Система документооборота для группы из 4 компаний. Этот документ — источник правды. Если код расходится с ним, либо исправляется код, либо осознанно меняется документ (с ADR).

---

## 1. Принципы

1. **Сервер никому не доверяет.** Всё, что приходит от сайта, проверяется заново. Сайт только показывает.
2. **Компании изолированы дважды:** фильтром в коде и Row-Level Security в PostgreSQL.
3. **Доступ проверяется дважды:** политикой в коде и фильтром внутри SQL.
4. **Роли, разделы, документы и шаблоны — это данные**, а не код. Новый документ или роль не требует программиста.
5. **Утверждённый документ не меняется никогда.**
6. **Каждый повтор безопасен:** двойной клик, повтор запроса, повтор задачи не создают дублей.
7. **Тяжёлая работа — только в очереди.** HTTP-запрос не ждёт рендера, конвертации и выгрузок.
8. **API без состояния:** масштабируется добавлением копий.
9. **Любой сбой виден сразу:** метрики, логи, трассировка, алерты.

## 2. Общая схема

```
                      Браузер (кэш React Query)
                                 │
                 nginx / CDN: статика и логотипы из кэша
                                 │
                 Балансировщик (nginx, least_conn)
              ┌──────────┬───────┴──────┬──────────┐
            api #1     api #2   ...   api #N         ← без состояния
              └────┬─────┴──────┬───────┘
                 Redis       PgBouncer
            (кэш, лимиты,    ┌───┴────┐
               очереди)   Primary   Replica
                 │        (запись)  (чтение)
        ┌────────┼─────────┬─────────┐
     worker  converter  scheduler   relay
             (docx→pdf)
                 │
               MinIO  ←── браузер грузит и скачивает файлы напрямую
```

| Процесс | Что делает | Масштабирование |
|---|---|---|
| `api` | HTTP API | N копий за балансировщиком |
| `worker` | фоновые задачи | N копий |
| `converter` | docx → pdf, превью | отдельный пул с лимитом параллельности, без сети |
| `relay` | outbox → очередь | 1–2 копии (`FOR UPDATE SKIP LOCKED`) |
| `scheduler` | задачи по расписанию | один активный экземпляр (лидер через блокировку в Redis/PG) |

## 3. Мультикомпанийность

- Одна база, у каждой записи данных компании есть `company_id NOT NULL`. Он первый в каждом индексе.
- Каждая транзакция: `SET LOCAL app.company_id = '<uuid>'`. На всех таблицах компании — политика RLS `company_id = current_setting('app.company_id')::uuid`. Роль приложения в БД без `BYPASSRLS`. С PgBouncer в режиме transaction это работает, потому что `SET LOCAL` живёт внутри транзакции.
- `company_id` берётся только из токена.
- Роли выдаются внутри компании: `user_company_roles(user_id, company_id, role_id)`. Один человек может быть юристом в компании А и работником в компании Б.
- Вход: если роли только в одной компании — сразу в неё; если в нескольких — выбор. Смена компании = новый access-токен.
- Брендинг компании: логотип, цвета, название, реквизиты. На сайте применяется через CSS-переменные и тему Ant Design, в документах — через `{{company.*}}` и `{{company.logo}}` в шапке шаблона.
- Шаблоны общие для всех компаний. Компания может переопределить шаблон для себя; поиск: переопределение компании → общий.
- Нумерация, справочники, календарь, настройки — свои у каждой компании.

## 4. Роли и права

**Право** = `раздел.профиль.действие`, например `hr.sensitive.view`, `finance.standard.create`, `*.*.approve`.

Действия: `create`, `view`, `edit`, `submit`, `visa`, `approve`, `sign`, `archive`, `cancel`, `export`, `manage_templates`.

**Системные роли** (из `catalog/roles.yaml`, загружаются `seed`):

| Роль | Права |
|---|---|
| Админ платформы | компании, общие шаблоны; документы не видит |
| Админ компании | пользователи, роли, брендинг, шаблоны своей компании; документы не видит |
| Директор | видит всё в компании с момента отправки на утверждение, утверждает |
| Руководитель раздела (×11) | всё в разделе, визирует, правит шаблоны раздела |
| Специалист раздела (×11) | создаёт и видит документы раздела; `sensitive` — по допуску |
| Главный бухгалтер | руководитель финансов + вторая подпись |
| Руководитель подразделения | согласует заявки подчинённых, видит документы отдела |
| Работник | свои документы, заявки (`self-service`), ознакомление |
| Аудитор (по желанию) | только чтение утверждённых |

**Свои роли** админ компании собирает в конструкторе галочками «раздел × профиль × действие».

Заместитель директора — не роль, а делегирование на период (`delegations`).

Правила ролей:
- Нельзя менять собственные роли. Выдача ролей директора и админа — через запрос с подтверждением второго человека.
- Смена ролей увеличивает `token_version` → старые токены недействительны сразу; кэш прав сбрасывается.
- Уволенный или заблокированный: доступ пропадает сразу, его черновики переходят руководителю раздела.

## 5. Доступ к документам

### Профили

| Профиль | Что это | Примеры |
|---|---|---|
| `standard` | обычные документы раздела | приказы, договоры, накладные, акты |
| `sensitive` | узкий круг | оклады, взыскания, решения участников, кредиты, инциденты ИБ, несчастные случаи |
| `policy` | положения и политики: читают все, ознакамливаются | Правила ТР, политика ИБ |
| `register` | журналы и реестры: собираются сами или ведутся записями | журнал приказов, реестр договоров |
| `self-service` | подаёт любой работник | заявления, заявки на закупку/ремонт/ИТ/доступ/оплату, авансовый отчёт |
| `external` | загружаются из других систем, не генерируются | ЭСФ, налоговые формы, фин. отчётность, платёжки, ПСД |

### Пять путей доступа

Документ открывается, только если выполнен хотя бы один путь:

1. **Раздел:** роль имеет право `раздел.профиль.view`.
2. **Автор.**
3. **Субъект:** документ о пользователе (приказ о нём, доверенность на него) — только после утверждения.
4. **Участник маршрута:** визирует, утверждает, подписывает.
5. **Руководитель субъекта:** для документов подчинённых, кроме `sensitive`.

И всегда дополнительно: `confidentiality ≤ допуск` и документ не удалён.

### Правила

- По умолчанию запрещено. Чужой документ → `404`.
- Черновики видят только автор и руководитель раздела. Директор видит документ с момента отправки на утверждение.
- Нельзя создавать, визировать и утверждать документ о себе (кроме своих заявлений). Кто утверждает документы о самом директоре — настройка компании.
- Справочник сотрудников: краткая карточка (ФИО, должность, отдел) видна всем для выбора в формах; полная (ИИН, оклад, адрес) — HR и директору.
- Каталог «Создать документ», меню и списки фильтрует сервер.
- Реализация: `internal/access/policy` (проверка одного документа) и `internal/access/scope` (фильтр для SQL, тот же набор путей).

## 6. Каталог и шаблоны

### Каталог (`catalog/`)

- `sections.yaml` — 11 разделов и подразделов; меню сайта строится из API на их основе.
- `profiles.yaml` — 6 профилей.
- `roles.yaml` — системные роли.
- `series.yaml` — серии номеров (К, ОД, ТД, Д, Дов, Исх, Вх, Фин, Зак, Скл, ...).
- `documents/NN-<раздел>.yaml` — описание каждого документа:
  - `id`, название, тип (`template` / `register` / `upload` / `external`);
  - профиль доступа, серия номера, маршрут согласования, требуется ли подпись и ознакомление;
  - уровень конфиденциальности, срок хранения;
  - в каких разделах показывается (один тип документа может быть в нескольких разделах);
  - отметка «влияет на оплату»;
  - эффекты после утверждения (например, изменить оклад сотрудника);
  - `reviewed: true/false` — проверен ли текст юристом.
- `templates/<раздел>/<документ>/` — `template.ru.docx`, `template.kk.docx` (если нужен), `fields.yaml`.
- `templates/_common/` — общие поля и блоки: шапка с логотипом, подпись, ознакомление, водяной знак.

### Поля шаблона

| Источник | Примеры |
|---|---|
| автоматически | компания, реквизиты, логотип, директор, номер, дата, город |
| из справочника | сотрудник → ФИО, должность, отдел, ИИН; контрагент → БИН, адрес, банк |
| вручную | даты, суммы, причины, тексты |
| вычисляемые | дата окончания отпуска по календарю, сумма прописью |

### Версии

- Шаблон в репозитории — стартовый набор. Дальше руководитель раздела загружает новую версию через админку.
- Созданный документ всегда ссылается на версию шаблона, по которой создан.
- `make check-catalog` проверяет: у каждого документа есть профиль и серия; каждое поле в docx описано в `fields.yaml` и наоборот; шаблон собирается с тестовыми данными.

## 7. Жизненный цикл документа

```
Создание      форма → снимок всех полей + версия шаблона → черновик с водяным знаком
Согласование  визы по маршруту → директор
Утверждение   номер из серии → финальный PDF с номером → SHA-256 → документ заморожен
Подпись       ЭЦП (NCALayer, проверка на сервере) или скан с живой подписью
Эффекты       изменения карточки сотрудника — в дату вступления
Ознакомление  отметка в системе или скан листа
Хранение      удалить нельзя до конца срока хранения
```

Статусы: `DRAFT → IN_REVIEW → APPROVED → SIGNED → ARCHIVED`; `IN_REVIEW → REJECTED → DRAFT`; `APPROVED/SIGNED → CANCELLED` (только другим документом, со связью и откатом эффектов).

- Номер присваивается при утверждении, в той же транзакции, счётчик `компания × серия × год` под `FOR UPDATE`.
- Финальный PDF собирается из того же снимка, что видел директор, плюс номер и дата.
- Связи: основание (заявление → приказ), доп. соглашения, отмена, претензия → ответ.
- Входящие документы регистрируются с серией Вх.

## 8. Гонки и повторы

| Ситуация | Защита |
|---|---|
| Два утверждения одновременно | `SELECT ... FOR UPDATE` + проверка перехода + `UNIQUE` на решение по версии |
| Директор смотрел старую версию | в запросе `version_id`; не текущий → `409` |
| Два редактирования одновременно | `lock_version`; не совпал → `409` |
| Двойной клик / повтор запроса | `Idempotency-Key` на создающих `POST`; сохранённый ответ возвращается повторно |
| Параллельная нумерация | счётчик под блокировкой + `UNIQUE(company_id, series, year, number)` |
| Повтор фоновой задачи | задача проверяет «уже сделано?» перед работой |

## 9. Аутентификация

- Пароли: argon2id.
- Access-токен 10 минут, в памяти сайта. Содержит `user_id`, `company_id`, `token_version`, но не список прав (права — из кэша).
- Refresh: httpOnly, Secure, SameSite=Strict; ротация при каждом использовании; повторное использование старого → отзыв всей цепочки (`family_id`).
- `token_version` сверяется в middleware с Redis (кэш ≤ 30 с).
- 5 неудачных входов → блокировка на 15 минут; rate limit по IP; одинаковый ответ.
- CSRF: SameSite=Strict + заголовок для `/refresh` и `/logout`.

## 10. Файлы

```
1. POST /documents/:id/files    → проверка прав и лимитов → подписанный PUT (10 мин,
                                   фиксированные размер и тип)
2. Браузер грузит файл в MinIO напрямую
3. POST /files/:id/confirm      → сервер проверяет объект: есть, размер, SHA-256
                                 → событие в outbox
4. worker: filetype → antivirus → preview → ocr
5. GET /files/:id/download      → только CLEAN → подписанный GET (2 мин) → запись в аудит
```

- Бакет закрыт, публичного доступа нет. Логотипы — отдельный бакет с публичным чтением через nginx-кэш.
- Незавершённые загрузки старше 24 часов удаляются.
- Конвертер: отдельный контейнер без сети, лимиты памяти и времени, ограничение параллельности.

## 11. События и очереди

- Изменение данных и событие пишутся в `outbox` в одной транзакции. `relay` переносит в `asynq` (`FOR UPDATE SKIP LOCKED`), помечает отправленные.
- Очереди по приоритету: `critical` (уведомления, эффекты), `default` (рендер, проверка файлов), `low` (превью, OCR, выгрузки, пересчёт счётчиков).
- Справедливость между компаниями: лимит одновременных задач одной компании, чтобы массовая загрузка одной не блокировала остальных.
- Повторы с растущей паузой, 5 попыток, затем «мёртвая» очередь с алертом.

## 12. Кэш

JSON — это формат обмена данными, а не кэш. Кэш устроен так:

| Уровень | Что хранит | Как обновляется |
|---|---|---|
| Браузер (React Query) | списки, карточки, каталог, брендинг | списки ~30 с, каталог ~1 ч; инвалидация после мутаций |
| nginx / CDN | JS, CSS, шрифты, логотипы | имена файлов с хешем → кэш на год |
| Redis | права пользователя, брендинг, счётчики главного экрана, `token_version`, rate limit | TTL + сброс по событию через Pub/Sub |
| Память процесса | каталог, версии шаблонов | версии неизменны: новая версия = новый ключ |
| HTTP ETag | каталог, справочники, брендинг | `304 Not Modified` |

Каждый ключ содержит `company_id`. Все ключи описаны в одном месте (`internal/cache/keys`).

## 13. База данных и производительность

- PgBouncer в режиме transaction; пул в приложении ограничен.
- Запись — primary, чтение списков, реестров, поиска, отчётов — реплика. Чтение сразу после своей записи — с primary.
- Индексы: `company_id` первым; под каждый список и фильтр.
- Секционирование по месяцам: `audit_log`, `outbox`, `notifications`.
- Пагинация курсорная, максимум 100.
- `statement_timeout` 5 с для запросов API.
- Поиск: `tsvector` + GIN, фильтр доступа внутри запроса. При росте — OpenSearch, без изменения API.

### Лимиты

| Что | Значение |
|---|---|
| Тело JSON | 1 МБ |
| Файл | 50 МБ (настраивается по типу документа) |
| Запросы пользователя | 60/мин, загрузки 10/мин |
| Запросы компании | общий лимит, настраивается |
| Вход с IP | 10/мин |
| HTTP-сервер | ReadHeader 5 с, Read 15 с, Write 30 с, Idle 60 с |

Превышение → `429` с `Retry-After`.

## 14. Устойчивость

- Breaker и повторы для внешних сервисов (почта, Telegram, ЭЦП, 1С).
- Bulkhead: отдельные лимиты на тяжёлые операции, чтобы они не забирали ресурсы у обычных запросов.
- Плавная остановка: процесс перестаёт принимать новые запросы, дожидается текущих, затем выходит.
- Выкатка по одной копии; миграции только обратно совместимые (добавить → перейти → удалить старое в следующем релизе).

---

## 15. Безопасность данных

- ИИН, оклады, адреса шифруются на уровне поля; маскировка на сайте; просмотр пишется в аудит.
- `audit_log` только на добавление: у роли приложения нет `UPDATE`, `DELETE`, `TRUNCATE`.
- Утверждённые документы: нет физического удаления, только `deleted_at` после срока хранения.
- Логи без паролей, токенов, ИИН, окладов, содержимого документов.
- nginx: HTTPS, HSTS, CSP, X-Frame-Options и другие заголовки безопасности.
- Персональные данные сотрудников, по всей видимости, должны храниться на территории Казахстана — серверы и бэкапы размещаются там (подтвердить у юриста).
- `docs/threat-model.md`: каждая угроза → где закрыта → каким тестом.

---

## 16. Наблюдаемость и эксплуатация

- Метрики (Prometheus), дашборды (Grafana), логи (Loki), трассировка (Tempo/Jaeger).
- Алерты: 5xx > 1 %, p95 > 1 с, очередь растёт, outbox не отправляется > 1 мин, мёртвые задачи > 0, найден вирус, всплеск 403/404 от одного пользователя, диск > 80 %, бэкап не выполнен.
- Бэкапы: PostgreSQL с WAL (восстановление на любую минуту), MinIO — репликация. Еженедельный автоматический тест восстановления.

### Этапы роста

| Этап | Схема |
|---|---|
| 1. Старт | один сервер, Docker Compose, 2 копии `api` |
| 2. Рост | 2+ сервера приложений, отдельный сервер БД с репликой |
| 3. Большая нагрузка | Kubernetes, автомасштабирование `api`, `worker`, `converter`, кластер MinIO |

Переход между этапами меняет только `infra/`, не код.

## 18. Тестирование

| Тип | Что проверяет |
|---|---|
| Юнит | доменные правила, переходы статусов, политика доступа, сумма прописью, ИИН/БИН, даты |
| Интеграционные | на настоящем PostgreSQL (testcontainers): SQL, RLS, транзакции, блокировки |
| Изоляция | каждый эндпоинт: чужая компания → 404, без изменений |
| Матрица доступа | генерируется из каталога: документ × роль × черновик/утверждён × автор/субъект/чужой |
| Гонки | параллельные утверждения, нумерация, редактирование; `go test -race` |
| Шаблоны | каждый шаблон × каждая компания собирается; логотип и реквизиты на месте |
| E2E | заявление → приказ → утверждение → подпись → ознакомление → эффект |
| Нагрузка | k6: 4 компании одновременно; цели в `docs/roadmap.md`, этап 9 |

Правило: новый эндпоинт без тестов изоляции и доступа не принимается.
