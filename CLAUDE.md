# DocFlow — правила проекта

Этот файл читается в начале каждой сессии. В нём то, что не меняется: цель, стек, неприкосновенные правила и порядок работы.

- Архитектура (источник правды): `docs/architecture.md`
- План работ по этапам с критериями приёмки: `docs/roadmap.md`
- Текущее состояние: `PROGRESS.md` (ты ведёшь его сам)
- Исходный список документов: `catalog/source/documents-list.txt`

Если что-то в задаче противоречит этим файлам — не выбирай молча, скажи о противоречии.

---

## 1. Что мы строим и почему важна точность

Веб-система документооборота для группы из **4 компаний в Казахстане**.

- Сотрудник входит по логину и паролю, работает внутри своей компании и видит только то, что разрешают его роли.
- Документы создаются из шаблонов: пользователь выбирает документ в каталоге, заполняет форму, система подставляет логотип и реквизиты компании, данные сотрудников и контрагентов и собирает Word/PDF.
- 11 разделов: HR, юридический, корпоративное управление, финансы, закупки и продажи, склад и логистика, АХО, проекты, ИТ и ИБ, HSE, маркетинг. Около 350 типов документов.
- Документы проходят согласование, утверждение директором, получают номер, подписываются (ЭЦП или бумага), по ним ведутся ознакомление, журналы и реестры.

Пользователи — кадровики, юристы, бухгалтеры, руководители. Ошибка доступа — это утечка персональных данных или коммерческой тайны другой компании. Ошибка в номере, дате или сумме утверждённого документа имеет юридические последствия. Поэтому **корректность важнее скорости**: лучше сделать меньше, но проверенно, чем много и с дырами.

## 2. Стек

Стек зафиксирован. Новые зависимости — только через ADR в `docs/adr/` (зачем, какие альтернативы, почему эта). Точные версии фиксируются в `go.mod`, `package-lock.json`/`pnpm-lock.yaml` на этапе 0 и дальше меняются только осознанно.

**Сервер:** последняя стабильная версия Go · `chi` · `pgx/v5` · `sqlc` · `goose` · `asynq` · `minio-go` · `golang-jwt/jwt/v5` · `log/slog` · `go-playground/validator` · `oapi-codegen` · `shopspring/decimal` для денег.

**Данные:** PostgreSQL 16+ · PgBouncer · Redis 7+ · MinIO.

**Сайт:** React + TypeScript (`strict: true`) · Vite · TanStack Query · React Router · Ant Design (тема через токены компании) · CSS Modules + CSS-переменные · `openapi-typescript` для типов API.

**Генерация документов:** библиотеку для подстановки полей в `.docx` выбери на этапе 0 и оформи ADR. Обязательные требования, проверенные тестами:
- плейсхолдер, который Word разбил на несколько `run` (`{{emp` + `loyee.name}}`), подставляется правильно;
- таблицы с повторяющимися строками (спецификация, список сотрудников);
- вставка изображения (логотип компании) в колонтитул;
- казахские буквы (ә ғ қ ң ө ұ ү һ і) сохраняются в docx и корректно отображаются в PDF — шрифты в контейнере конвертера это поддерживают.

Если на Go нет надёжного варианта — вынеси рендер в отдельный сервис в контейнере `converter` и обоснуй в ADR.

**Язык:** идентификаторы в коде — английский. Комментарии, документация, сообщения об ошибках для пользователя, интерфейс — русский (казахский добавляется позже через i18n, закладывай его сразу: никаких строк интерфейса в коде компонентов).

## 3. Неприкосновенные правила

Каждое правило существует потому, что его нарушение — это реальный баг, который трудно найти потом. Нарушать нельзя, даже если так быстрее. Если правило мешает — остановись и объясни почему.

### 3.1. Изоляция компаний
- В каждой таблице с данными компании есть `company_id NOT NULL`, и он первый в каждом индексе.
- Каждая транзакция выполняет `SET LOCAL app.company_id = ...`, и на всех таких таблицах включён Row-Level Security. Приложение подключается к БД ролью **без** `BYPASSRLS`.
- `company_id` берётся **только** из токена, никогда из тела запроса, URL или заголовка.
- Каждый ключ кэша (Redis, React Query) содержит `company_id`.
- На каждый эндпоинт есть тест: пользователь компании А не может ни прочитать, ни изменить, ни узнать о существовании данных компании Б.

### 3.2. Доступ
- Вся логика доступа — только в `internal/access`. В обработчиках и сервисах нет проверок вида `if role == "hr"` — только вызов политики с правом (`hr.sensitive.view`).
- Роли — это данные (набор прав), а не константы в коде.
- Доступ проверяется дважды: политикой в сервисе **и** фильтром внутри SQL-запроса. Списки, поиск, реестры и счётчики фильтруются в SQL, а не циклом после выборки.
- По умолчанию запрещено. Чужой документ возвращает `404`, а не `403`.
- Субъект документа (работник, о котором приказ) видит его только после утверждения. Нельзя создавать, визировать и утверждать документ о самом себе (кроме своих заявлений).

### 3.3. Слои
- `handler` — только HTTP: разобрать, провалидировать, вызвать сервис, вернуть ответ.
- `service` — бизнес-логика, транзакции, политика доступа.
- `repository` — только SQL через `sqlc`. Никакой конкатенации строк в SQL.
- `domain` ничего не импортирует из `http`, `storage`, `modules`.
- Сайт ничего не решает: права, статусы, номера, суммы считает сервер.

### 3.4. Утверждённый документ неизменен
- При создании сохраняются **снимок всех значений полей** и **версия шаблона**. Изменение справочника (фамилия, директор, реквизиты) не меняет уже созданные документы.
- Номер присваивается **при утверждении** из счётчика `компания × серия × год` под блокировкой строки. Дыр и дублей быть не может, это покрыто тестом.
- После номера финальный PDF собирается из того же снимка, сохраняется его SHA-256. Дальше документ не редактируется: только новая версия или отмена другим документом.
- Физического удаления нет: `deleted_at` и сроки хранения из каталога. Права `UPDATE`/`DELETE` на журнал аудита и утверждённые документы у роли приложения отозваны.

### 3.5. Гонки и повторы
- Смена статуса — транзакция с `SELECT ... FOR UPDATE`.
- Изменение документа — оптимистичная блокировка через `lock_version`; конфликт → `409`.
- Утверждение передаёт `version_id`, который видел директор; если он уже не текущий → `409`.
- Все создающие `POST` принимают `Idempotency-Key`.
- Уникальные ограничения в БД — последняя линия защиты (одно решение на версию, уникальный номер в серии).

### 3.6. События и фоновые задачи
- Событие пишется в `outbox` **в той же транзакции**, что и изменение данных. В очередь его переносит `relay`.
- Каждая задача идемпотентна: повторный запуск не создаёт дублей и не портит данные.
- Тяжёлая работа (рендер, конвертация, OCR, выгрузки) — только в очереди, никогда в HTTP-запросе.

### 3.7. Файлы
- Загрузка и скачивание — по подписанным ссылкам напрямую в MinIO, мимо API.
- Подтверждение загрузки проверяет в хранилище: объект существует, размер и SHA-256 совпадают.
- Тип файла проверяется по содержимому. Скачивание разрешено только после `scan_status = CLEAN`.
- Конвертер работает без сети, с лимитами памяти и времени.

### 3.8. Аутентификация
- Пароли — argon2id. Access-токен 10 минут, в памяти сайта. Refresh — httpOnly, Secure, SameSite=Strict cookie, ротация при каждом использовании, повторное использование старого → отзыв всей цепочки.
- `token_version` у пользователя: блокировка или смена ролей мгновенно делает все токены недействительными.
- Блокировка входа после 5 неудачных попыток, rate limit на вход по IP. Ответ всегда одинаковый: «неверный логин или пароль».

### 3.9. Деньги, даты, текст
- Деньги — `numeric` в БД и `decimal` в Go. `float` для денег запрещён. Валюта хранится рядом с суммой.
- Моменты времени — `timestamptz` в UTC. Даты документов — `date`. Часовой пояс — из настроек компании (проверь, что tzdata актуальна: с 2024 года весь Казахстан в UTC+5).
- «Сумма прописью» на русском и казахском — отдельная функция с табличными тестами (0, 1, 2, 5, 11, 21, 1 000, 1 000 000, дробные тиыны).
- ИИН и БИН проверяются по контрольной цифре.

### 3.10. Персональные данные и логи
- ИИН, оклады, адреса шифруются в БД на уровне поля. На сайте маскируются, просмотр полного значения пишется в аудит.
- В логах нет паролей, токенов, ИИН, окладов, содержимого документов.
- Секреты — только из переменных окружения. В репозитории их нет.

### 3.11. Лимиты
- У каждого HTTP-сервера таймауты, у каждого запроса к БД `statement_timeout`, у каждого внешнего вызова — таймаут и breaker.
- Тело JSON ≤ 1 МБ, `DisallowUnknownFields`. Размер страницы ≤ 100, пагинация курсорная.
- Rate limit по пользователю **и** по компании.

## 4. Как работать

1. **Начало сессии.** Прочитай `CLAUDE.md`, `PROGRESS.md`, текущий этап в `docs/roadmap.md`, последние коммиты (`git log --oneline -20`). Запусти `make check`, чтобы знать исходное состояние.
2. **План перед кодом.** Для этапа напиши `docs/plans/phase-NN.md`: какие файлы, миграции, эндпоинты, тесты; какие риски; какие вопросы. Если рядом человек — покажи план и дождись подтверждения.
3. **Маленькие шаги.** Шаг → тесты → `make check` → коммит. Не накапливай большой несобранный кусок.
4. **Тесты вперёд.** Для нового эндпоинта сначала тесты изоляции компаний и доступа, потом реализация.
5. **Красные тесты чинят код, а не тест.** Тест меняется, только если он сам неверен — и это объясняется в сообщении коммита. Никаких условий «если это тест, то...», никаких отключённых проверок, никаких `t.Skip` без записи в `PROGRESS.md`.
6. **Никаких заглушек, выдающих себя за готовое.** Не сделано — значит `// TODO(phase-NN): что именно` и строка в разделе «Не сделано» в `PROGRESS.md`.
7. **Не расширяй объём.** Делай только текущий этап. Идеи на будущее — в `docs/ideas.md`.
8. **Неясность.**
   - Решение легко отменить → выбери безопасный вариант, запиши в `docs/questions.md` с пометкой «принято по умолчанию» и продолжай.
   - Решение трудно отменить (схема данных, формат номера, модель прав, юридический текст) → остановись и спроси.
9. **Юридические тексты не выдумывай как окончательные.** Шаблон содержит структуру и поля из `fields.yaml`, а текст помечен `ЧЕРНОВИК ТЕКСТА — ПРОВЕРИТЬ ЮРИСТУ`. Проверенные юристом шаблоны помечаются в каталоге `reviewed: true`.
10. **Миграции.** Применённую миграцию не редактируют — только новая. У каждой есть `down`, и `up → down → up` проходит в тесте.
11. **Сгенерированный код** (`sqlc`, `oapi-codegen`, `openapi-typescript`) руками не правится. CI проверяет, что `make gen` не даёт изменений.
12. **Коммиты** маленькие, по смыслу, в стиле Conventional Commits.
13. **Контекст.** Если сессия становится длинной — обнови `PROGRESS.md` так, чтобы новая сессия могла продолжить только по нему.

## 5. Проверка перед словом «готово»

Ничего не называется готовым без запуска проверок. Нельзя писать «тесты проходят», если ты их не запускал в этой сессии.

`make check` запускает:
- `golangci-lint`, `go vet`, `govulncheck`
- `go test -race ./...` (интеграционные тесты — на настоящем PostgreSQL через testcontainers, не на моках)
- `tsc --noEmit`, линтер и тесты сайта
- `make check-catalog`: каждый документ каталога имеет профиль доступа, серию, шаблон; каждое поле в `.docx` есть в `fields.yaml` и наоборот
- `make gen` без изменений в git
- миграции `up → down → up`

Для этапов с интерфейсом — e2e-тест основного сценария этапа.

## 6. Качество кода — чек-лист

**Go**
- `context.Context` первым аргументом везде, где есть ввод-вывод; таймауты через контекст.
- Ошибки оборачиваются `fmt.Errorf("...: %w", err)`; доменные ошибки маппятся в HTTP-коды в одном месте (`http/response`).
- Нет `panic` в обработке запросов; recover-middleware — страховка, а не механизм.
- Нет утечек горутин: у каждой горутины есть способ завершиться; плавная остановка по сигналу.
- Время — через интерфейс `Clock`, чтобы тестировать сроки и даты.
- Нет N+1 запросов; для списков в PR прикладывается `EXPLAIN ANALYZE` на объёме тестовых данных.

**SQL**
- Каждый запрос к данным компании содержит `company_id` и фильтр доступа.
- Индексы под каждый список и фильтр; секционирование по месяцам для `audit_log`, `outbox`, `notifications`.
- Ограничения целостности в БД (`NOT NULL`, `CHECK`, `UNIQUE`, внешние ключи), а не только в коде.

**Сайт**
- Бизнес-правил нет. Кнопки показываются по правам с сервера, но защита — на сервере.
- Обработаны `401` (обновить токен, иначе на вход), `403`, `404`, `409` (показать «документ изменён, обновите»), `422` (ошибки полей), `429`, `5xx`.
- Кнопки мутаций блокируются на время запроса; каждая мутация отправляет `Idempotency-Key`.
- Ключи React Query содержат `company_id`; после мутации инвалидируются нужные ключи.
- Большие таблицы — виртуальные. Каждый раздел грузится лениво. Бюджет размера бандла проверяется в CI.
- Формы строятся из `fields.yaml`, валидация повторяет серверную (из схемы OpenAPI).
